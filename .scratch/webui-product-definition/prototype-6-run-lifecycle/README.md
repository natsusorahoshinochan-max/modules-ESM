# PROTOTYPE 6 — 运行范围、状态、失败与取消（一次性原型）

> 在继承原型 1 已采用的空间画布卡片方向下，用 `?variant=` 切换三种 Run 范围与生命周期信息结构。

## 决定 — 2026-08-30 采用方案 A

**原型 6 采用方案 A「空间范围叠层」作为后续正式界面设计的 Workflow 运行范围与生命周期表达方向。** 执行范围直接高亮在自由空间 Workflow 画布上；收起 Node Instance 在名称旁持续显示状态；运行范围、运行操作、节点详情与最近一次 Run 事件集中在相邻侧栏。

这是用户的明确选择；未提供额外选择理由，因此本文不推断理由。方案 B「运行账本」与方案 C「分支泳道」只作为一次性比较证据保留，不再是同等候选。本决定裁决整体信息结构，不裁决最终颜色、图标、视觉密度、进度与耗时表达、运行详情中的 evidence 深度、“无成功上游时从节点继续”的入口行为，或是否区分两类取消状态。

## 唯一产品问题

用户能否在开始前预测会运行什么，并在等待、运行、失败、继续、取消以及 Workflow 修改后，始终正确判断结果对应哪一版 Workflow？

本原型只对应 `docs/2026-08-29-webui-functional-spec.md` 第 4 节与第 5.1 节的“来自修改前的流程”标记。它不重新裁决 Workflow 画布结构，不建立生产运行器，也不验证 Results Workbench 的候选比较与筛选操作（这些属于原型 7）。

## 运行

```bash
.venv/bin/python .scratch/webui-product-definition/prototype-6-run-lifecycle/serve.py
```

打开 <http://127.0.0.1:4184/?variant=A>。

- `A` — **已采用。空间范围叠层**：直接在自由空间 Workflow 画布上高亮执行范围；右侧集中显示范围、节点详情和 Run 事件。
- `B` — 仅供比较。**运行账本**：用逐节点表格并列展示依赖、是否执行、状态、参数与已保留结果。
- `C` — 仅供比较。**分支泳道**：把共享上游、序列评估分支和结构评估分支分开，强调失败分支与整次取消的不同作用域。

所有状态只存在内存中，刷新即重置。页面顶部的“本轮模拟溶解度评分失败”、手动“推进一次”、重置按钮与原型状态检查器只用于走查，不是产品功能。模型、Method、Metric、生成数量、阈值、随机种子、PDB 与科学参数均明确标注为示意，不形成科学或产品决定。

## 正常路径

1. 关闭“本轮模拟溶解度评分失败”。
2. 分别选择“完整运行”“运行到节点”和“从节点继续”，点击不同 Node Instance，核对画布/账本/泳道高亮的精确范围。
3. 打开运行摘要，核对执行范围、模型、主要参数、生成数量、随机种子和阻止运行问题；确认后才开始。
4. 逐次点击“推进一次”，观察收起节点保持收起，只在名称旁显示等待、运行中和成功。
5. 运行完成后查看 Results；结果应归属于最近一次 Run 使用的 Workflow revision。

## 容易误解或失败的路径

1. 保持“本轮模拟溶解度评分失败”开启，完整运行到两个分支并行。
2. 推进到“评分溶解度”失败：依赖它的“筛选候选”必须标记为“未执行 · 上游失败”，独立结构分支继续并成功。
3. 点击失败状态查看详情，选择“模拟修正，然后从此节点继续”；运行摘要只列出失败节点与其下游，不重跑共享上游或已完成结构分支。
4. 重置后启动完整运行，在中途点击“取消整次 Run”；所有运行中与等待节点变成取消，已经成功的节点及其结果继续保留，界面没有单节点取消入口。
5. 在最近一次 Run 结束或取消后，双击顶部项目标题，模拟修改当前 Workflow 参数；Results 随即显示持续的“来自修改前的流程”标记，同时仍允许模拟导出。

## 原型边界

- 项目只显示最近一次 Run；原型没有历史 Run 列表。
- “失败”只阻断依赖该节点的下游；独立分支继续。
- “取消”只作用于整次 Run；没有单节点取消。
- 已成功节点的结果在失败或取消后继续保留。
- “从节点继续”必须有可复用的成功上游结果；若没有，运行摘要会列出并定位阻止运行的问题。
- Workflow 修改后，旧 Results 仍可查看和导出，但必须持续显示其 Workflow revision 来源。
- 具体 evidence 浏览深度、最终颜色、图标、运行耗时表达、默认 Metric 与科学值仍未裁决。

## 采用后的观察与仍待裁决

- 方案 A 已被采用：后续正式设计应把本次执行范围与 Node Instance 状态直接叠加在已采用的自由空间 Workflow 画布上，并把运行范围、操作、节点详情和最近一次 Run 事件组织在相邻侧栏。B、C 不再参与整体方案选择。
- B 最容易逐节点审计范围、依赖和保留结果，C 最直接解释“一个分支失败”和“取消整次 Run”的作用域差别；这些只保留为比较观察，不覆盖用户对 A 的选择，也不要求把 B/C 的整体结构混入正式方向。
- “从节点继续”在没有可复用的成功上游结果时是否应保持可选但在摘要中阻止、直接禁用入口，或改写为另一种操作，功能规格尚未明确。本原型采用“摘要中阻止并定位缺失上游”的保守占位行为，不把它记录为产品决定。
- 等待多久后显示耗时、进度或 Provider 细节，以及 Run 详情中 evidence 的浏览深度，仍未裁决；人工“推进一次”只用于暴露中间状态。
- 取消后，运行中与等待节点都统一显示“已取消”。若未来需要区分“运行中被取消”和“尚未开始即取消”，需另行产品裁决；当前功能规格没有要求这一区分。

## 功能规格影响

方案 A 的采用决定需要回写权威功能规格，作为第 4 节后续正式界面设计的结构方向。完整一次性比较材料捕获在 `codex/prototype-6-run-lifecycle` 分支；原型代码不成为生产实现基线。

本次选择不改变现有运行语义，也不裁决“无成功上游时从节点继续”的入口行为或两类取消状态是否需要区分。若用户后续裁决这些问题，再回写第 4.1、4.2 或 4.5 节。
