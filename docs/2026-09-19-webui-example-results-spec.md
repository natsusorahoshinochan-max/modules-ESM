# WebUI example result resource

The resource belongs only to the protected `webui-3gb1-example` Project. It is
generated by a fresh full Run of the shipped `webui-3gb1.example.json` Workflow
with its declared Bindings, Methods and seeds. The canonical verification
Workflow remains unchanged. A campaign's canonical 3GB1 result is not a substitute
for this distinct example.

## Portable evidence

The ZIP contains one manifest and the exact immutable owner records:

- Project Inputs: original reference, filename, digest and bytes.
- Workflow authoring records: original Draft, workspace and Commit records,
  including the original Commit ID, scientific definitions and scientific identity.
- Ledger: original ordered durable transaction bytes, with unchanged Project,
  Run, invocation, Candidate and artifact identities.
- Objects: the complete content-addressed closure of all published Node result
  manifests, Port manifests, typed values and artifact bodies.

The manifest lists resource paths and existing scientific object identities, and identifies
the Project, Workflow Commit, Run and original Run terminal cursor. Archive paths
are relative resource paths. A resource contains no replay-index cache, temporary
Provider workspaces, model weights, process environment, execution profile,
credential or private configuration. The declared resource layout and existing
owner provenance contracts determine what is included. Published scientific
evidence is copied unchanged; the exporter does not inspect arbitrary scientific
strings or artifact bodies to guess whether they contain a filesystem path.

The exporter requires a successful full Run with one executed disposition per
Workflow Node, no cache replay and no derived source. It reads the original
Ledger with `Ledger.load`, the original Commit with
`WorkflowAuthoringService.require_verified_commit`, Inputs with `ProjectManager`,
and objects through `ResultStore`/`ProjectObjectStore`. It copies existing Ledger
transactions; it never constructs transactions from public event projections.

## Installation and visibility

Before runtime registry construction, the installer copies trusted packaged owner
records directly, without a temporary Project, transport hashes, recompilation,
or replay-based proof. Original Input descriptors and object identities are reused.
It publishes immutable dependencies first and renames the complete Run directory last.
The Run cannot appear before its dependencies are available. Interrupted staging
does not create a partially visible Run. Reinstalling the same resource is
an immediate return once its Run is installed; a conflicting protected example or different existing Run is rejected
without overwriting it. User Projects and the canonical verification Project are
outside this installer.

The protected example remains read-only through ordinary authoring and Project
APIs. Copy-on-first-edit continues to use its explicit reference-results Project.
Installing evidence does not fabricate a new Run, relabel a prior Commit or
populate another Project's replay cache.

## Build and real execution

`verification.webui_example_evidence` owns the one-off generation/export commands.
Generation requires an explicit remote data root with no prior example Run and
an explicit acceptance execution profile; it performs the real full Run before
export. A failed/interrupted Run remains in that root for diagnosis and cannot be
exported as the bundled result. Export can read a previously completed generation
root without invoking Providers.

The complete result resource ships in the backend wheel for offline availability
on first open. Generation reports retain its measured size and original Run identity.
Changes to scientific definitions require a new real generation, not relabeling
existing evidence.

Port manifests carry
original candidate references and port identities so readers do not recompute them.
Production startup installs this resource unconditionally; the explicit
`load_example_results=False` composition option is used for example evidence
generation and isolated owner tests that require no preexisting example Run.

Verification runs remotely only: focused owner tests, a generated real example,
clean installed-package startup with Providers unavailable, readable original
Commit and full Run evidence, candidate/score/lineage/structure browsing, and
first-edit reference-results preservation. The three user journeys and the
canonical serial Provider campaign remain separate acceptance requirements.
