## 本轮结论

刚制作的 P1/P2 没有覆盖项目的主要操作对象和现有体验，不能作为本项目的用户原型交付。
P1 把自由编辑的 Workflow 缩成表单和预设按钮；P2 验证了真实渲染器调用，却离开了实际 Prompt 编辑过程。
界面能点击、渲染器能显示结构，不等于已经提供了可评价的蛋白研究工作台。

这次纠偏不意味着恢复全部旧设计为不可修改要求。
用户已明确允许重评科学契约、ADR、产品形态及新设计；A/B 主对象比较、Run 历史和跨次比较仍可继续研究。
问题在于两套新方案都承诺保留可编辑 Workflow，但 P1 连这个共同前提都没有实现。
因此，本轮演示无法说明“以 Workflow 为中心”或“以 Design Document 为中心”哪一种更适合用户。

下一轮必须在完整画布、Prompt Studio、Results 和项目入口组成的产品壳内评价变化。
优先复用已存在的功能闭环，改变信息层级、观感与操作路径；若要删减功能，必须把取舍明确写出。

现有默认画布不是简单的五个业务按钮。
它将 36 个计算节点、61 条边组织成五个阶段组及一个独立导出节点，保留 14 条跨组连接。
初始以 100% 缩放阅读；阶段导航和横向平移帮助定位，适合视图是用户主动选择的总览动作。
分组没有替换底层 Workflow，常用参数也没有另外保存一套值。

Prompt Studio 同样已经具有可用的复杂交互基础：五条轨道、结构同步选择、局部编辑、插入删除、撤销及整体保存。
结构操作约定包含 G 移动、R 旋转、B 框选、轴约束、数值输入、确认和取消。
这些能力决定原型应该解决怎样的真实操作负担，不能用两个轨道和几颗 CA 球代替后再评价产品形态。

## 已有状态能力与真正待验证的问题

[WorkspaceEditor](../../webui/src/workspace-editor.ts)已经区分 `desired` 与 `acknowledged`，具有保存队列和编辑撤销。
PromptStudio 的 `propose` 也已经用请求身份过滤过期预览。
后续仍可调整状态归属和接口，但不能把这些已有能力重新包装成原型新发现，再从零建立另一套工作台。

当前最具体的结构体验缺口是：G/R 输入经过 90ms 尾沿防抖调用后端预览，返回后由 3Dmol 清除并重新加载 PDB。
连续输入会延后请求，因此现状不是即时、逐帧的局部坐标反馈。
下一轮应在真实 Prompt 操作中验证临时坐标显示、确认／取消及镜头保持；渲染器更换仍须由证据决定。

Results 的勾选、筛选、排序保存为节点已经存在；“采用候选的指定轨道”和“跨 Run 比较”仍是新提案。
两者不能混写成已实现能力，也不应因本轮原型失败而直接取消。
它们应在完整研究旅程中说明新增入口、对象关系与操作后果，再决定是否继续。

## 下一轮先完成一条代表旅程

第一步先体验现有画布，再以同一份研究对象贯穿下面的过程：

1. 打开默认项目，阅读五阶段画布与跨阶段连线，定位需要修改的操作。
2. 修改组卡片的常用参数，进入对应组，确认实际节点中的值一致；保留自由增删和重连能力。
3. 从 Prompt 节点进入专用编辑器，用矩阵与结构视图完成一次可理解的条件修改。
4. 保存返回原 Workflow，恢复原来的组层级与工作位置，继续查看或修改流程。
5. 查看该流程关联的已发布结果，比较候选，调整筛选或勾选，并把选择保存为可编辑流程节点。

这条旅程首先复用默认示例已有的结果，不要求为了评价界面重新调用模型。
修改后必须保留结果的来源版本提示，不能让用户误以为旧结果来自刚修改的输入。
若原型使用模拟运行或新增设计能力，应在相应位置标注，且与实际已存在的结果区别清楚。

完成上述闭环后，再比较 A/B 的默认入口、导航和对象解释。
两个方案都必须保留完整 Workflow 的可达性和可编辑性；不能通过省略复杂任务让其中一个显得更简洁。
外观改进应帮助用户读懂阶段、节点参数、端口和选区，而不只是更换配色与卡片边框。
