```bash
MOTION_INTERVAL=20 /root/work/protein-review-447847ff.5NWQrH/.tools/node/bin/node \
  /root/work/canvas-prototype-20261005/diagnose-transform.mjs
```

| 输入节奏 | 实测移动时段 | 移动期间预览请求 | 移动期间 WebGL 绘制调用 | 结论 |
|---|---:|---:|---:|---|
| 每 20ms 一次，第一次 | 460ms | 0 | 0 | 连续移动时没有结构更新，检查失败 |
| 每 20ms 一次，重复 | 459.9ms | 0 | 0 | 同一症状再次复现 |
| 每 120ms 一次，对照 | 2767.6ms | 21 | 432 | 输入间隙变长后开始间歇更新 |

绘制调用数不等于帧数；对照成功也不代表已达到实时性能。这里的目的只是区分“持续移动没有绘制”和“有绘制但帧率较低”。运行环境为软件 WebGL，不作为用户机器的帧率基准。20ms 两次实验的首个预览响应耗时为 75ms、79ms；本测量发生于远端浏览器，不包含用户本地经 SSH 隧道的额外往返。

核对的原因依次是输入防抖、请求往返、完整结构重建。第一项由节奏对照确认：`StructureViewer.updateTransform` 每次移动清除上一个计时器，再等待 90ms 才调用 `onPreviewTransform`。连续移动会不断推迟请求。随后 `PromptStudio.previewTransform → propose → onPreview` 等待后端结果，生成新的 projection/PDB；StructureViewer 的 PDB effect 执行 `clear → addModel → render`。后两项增加反馈路径成本，但本轮没有分别测量解析与绘制耗时，不能据此宣称 renderer 是主要瓶颈。

建议的最小修正是：进入 G/R 时保留本次操作起点、选区和镜头；移动时使用已有变换矩阵，从起点坐标计算临时显示坐标，以 `requestAnimationFrame` 合并同一帧内的输入；Enter／左键确认后提交最终变换并接纳后端预览，形成一次编辑；Esc／右键取消恢复起点，不产生编辑。临时显示不冒充已确认的 Prompt 数据；确认失败应保留可调整或取消的操作状态。实现时还要避免迟到的旧预览覆盖当前拖动。

先在现有 3Dmol 上验证坐标更新，不建立新的渲染框架。验收应覆盖持续移动时真实坐标／画面更新、未选中原子保持不变、确认与取消、一次撤销、镜头保持、轴约束和数值输入。单纯把 90ms 改小无法移除网络依赖。这一诊断阶段未修改产品代码；随后的实现与验证见上方实施记录。

## 这次交付了什么

原型直接使用现有 App、默认五阶段流程、完整节点画布、Prompt Studio 和 Results。默认示例仍有 36 个计算节点、61 条连线；分组顶层展示五个阶段和导出节点、14 条跨阶段连线。来源添加、参数修改、端口连接、分组、复制、撤销及项目入口继续复用现有实现。

本轮新增的是这条实际操作路径：

**阶段／节点 → 精确输出 → 查看与比较候选 → 保存 Selection → 定位新增节点。**

- 画布上下文和节点卡片按节点、输出端口及值索引打开候选集合；不会把没有发布的目标偷偷换成另一个输出。
- Results 显示来源的组路径和节点名称，保留精确位置详情，可以回图定位来源节点。
- 勾选、筛选和排名沿用已有 Selection 保存方式；收到保存回执后显示新增节点入口。首次数值修改或 Selection 保存产生个人副本时，仍保留原 Run 的查看状态。
- Prompt 顶部说明正在编辑哪个项目、组和节点；五轨矩阵、结构视图与保存返回沿用现有编辑器。
- A 使用右侧检查栏，B 使用底部输出台；开发预览切换布局不重新挂载 App。节点库和输出区域可收起。

这里的 A/B 只比较布局，不等同于早期 Workflow / Design Document 对象模型方案。旧 P1/P2 保留为局部实验，不作为本次产品原型入口。
